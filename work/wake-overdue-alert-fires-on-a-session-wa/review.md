# verdict: request_changes

Pulling two fixes inline per the grader and the operator's call. My prior approve rested on a misread of `Wake.report_overdue`: I rejected "skip take_wakes while a submit is pending" twice on the claim it would sit wakes past the overdue window and bring back the false alarm. But `report_overdue` only deletes/reports a wake when `inserted_at < 300s` **AND** `not exists(busy)` — `busy` being `thinking_since > now - 600s`. The presence fix (the ~180 s heartbeat refreshing `thinking_since`) keeps the seat busy for the whole held submit, so sitting wakes are skipped by the guard, not reported. Skip-take is safe. Correcting the call.

## required to merge

1. **#547 — skip take_wakes while a submit is pending (restores the file invariant).** The file header (line 7) states the module's variables are "lost on a reload, never a queue of unsent work." The current `submitting` chain is exactly a queue of unsent work — wakes taken from the server and held in memory, lost on reload/crash during a held submit, and the change widens that window from the one mid-submit wake to every wake that arrived during the hold. Fix: add a `pendingSubmits` counter that `submitWakes` increments before the async submit and decrements in the chain's `finally`; `drainWakes` returns early (before `take_wakes`) while `pendingSubmits > 0`. Wakes that arrive during a held submit then stay on the server (durable, survive reload/crash), and only the single mid-submit wake is in-flight at a time — matching the header's "a wake whose submit fails is put back for the next poll." The `submitting` chain can stay to serialize that one in-flight submit, but the queue must never hold more than one wake.

2. **#547 tests — re-specify the hung-submit test.** Its current `expect(take_wakes).toBeGreaterThanOrEqual(2)` is wrong for this fix: skip-take means fewer takes, not more, so the old assertion is vacuous against the new behaviour. Assert instead: first wake taken + submitted (held); a second wake arriving during the held submit is NOT taken (stays on the server); release the held submit, then the next poll takes and submits the second; both deliver in order — `submitted` equals `["wake one", "wake two"]`. Add a `session.end`-before-release case: a wake that arrived during the held submit survives `session.end` (still on the server / put back, not lost).

3. **presence_thinking drop — test + pr.md note.** `turn.start` now gates `declare($, "presence_thinking")` on `!e.agentId`, so a subagent's turn.start no longer declares it. This is an undocumented behaviour change bundled in (grader scope-3). Add a test pinning the intended behaviour: a `turn.start` with `agentId` declares no `presence_thinking` (the main turn's presence is in effect; subagents are tracked in `running` + the heartbeat). State the choice in pr.md.

4. **STALE_REFRESH_TICKS comment.** One line next to `const STALE_REFRESH_TICKS = 60`: it's ~180 s at 3 s/poll, kept under the server's 600 s stale-turn clock (`Server.Presence.Thinking.stale_turn_seconds/0`), so the heartbeat refreshes `thinking_since` before `report_overdue`'s `not exists(bussy)` guard can fail.

## non-blocking follow-ups (replace the prior set — all filed, held)

1. **#545 (med, held) — a never-completing subagent pins the seat busy.** A subagent that crashes or aborts without `turn.complete` stays in `running` until `session.end`, so `presence_idle` never fires and the heartbeat runs forever — a regression this change introduces (the opposite false state from #532). Fix: store each `agentId` with the tick it started and drop entries older than a bound in the `WAKE_POLL_MS` clock callback, with a `note()` line; also reset `mainEnded` and `waitTicks` in `session.end`. Test: `turn.start` with agentId, main `turn.complete`, advance the clock past the bound, expect one `presence_idle`.

2. **#546 (med) — prove live.** Launch a citizen, background a subagent, confirm `turn` events carry `agentId` live (so the running-set path engages) and the seat stays off the overdue clock.

3. **#548 (low, held, blocked by #545) — waitTicks drift.** `waitTicks` is module-level, only incremented, never reset, so a second wait's first refresh fires at `60 − N%60` rather than 60. Non-functional (max gap stays under 180 s against the 600 s clock). Reset on main `turn.start`, with a two-waits test.

None of these three blocks the re-build; #545 is the next build after this lands.
